# Модель загроз STRIDE

Активи: облікові дані MQTT, приватні ключі, достовірність вимірів і команд,
доступність охолодження/сигналізації, історія аварій. Межі довіри: пристрій ↔ брокер,
брокер ↔ openHAB, користувач ↔ UI, Docker/файлова система хоста.

| Категорія | Конкретна загроза | Протидія у проєкті | Залишковий ризик |
|---|---|---|---|
| S — Spoofing | Сторонній клієнт прикидається сенсором hot | Окремі випадкові паролі, anonymous=false, TLS із перевіркою CA/hostname | Викрадений пароль дозволяє видавати себе за відповідний пристрій до ротації |
| T — Tampering | Зміна температури або команд у мережі | TLS 1.2+, hostnameValidated, власний CA | Компрометований сам сенсор може надсилати хибні дані у свій дозволений топік |
| T — Tampering | Користувач cold публікує команду кондиціонеру | ACL дає cold лише власні telemetry/status; перевірка негативного PUBACK | Власний пароль openHAB дає керування двома актуаторами; його слід захищати |
| R — Repudiation | Заперечення надсилання аварії/команди | Журнал підключень брокера, MQTT username, openHAB events та повідомлення зі зміною причин | Локальні логи не є незмінним криптографічним аудитом; для production потрібен зовнішній збирач |
| I — Information disclosure | Перехоплення паролів/показників або публікація ключів у git | TLS, .gitignore, runtime поза архівом, CA key не монтується, UI на localhost | Адміністратор хоста має доступ до секретів; .env потрібно окремо захищати |
| D — Denial of service | Завислий сенсор лишає стару температуру, хоча TCP-сесія жива | Freshness watchdog >60 с, окрема тривога навіть при status=online | Відмова брокера/openHAB потребує незалежного зовнішнього нагляду |
| D — Denial of service | Великий пакет або переповнення черги | max_packet_size=8192, обмеження queued/inflight, команда не більше 512 B, локальна мережа | Обмеження пакетів не є повним rate limiting; захист від розподіленої атаки не реалізовано |
| E — Elevation of privilege | Сенсор читає чужі дані або керує актуатором | ACL із default deny, мінімальні точні шляхи, окремий admin | Компрометація спільного simulator-контейнера відкриває всі device-credentials у ньому |

## Перевірка

`scripts/security_check.py` виконує реальні негативні спроби підключення/публікації.
Звичайний TCP healthcheck не перевіряє ні пароль, ні ACL: для цього є окремі тести.
У UI не передбачено відключення правила протікання; ручна команда OFF сирені буде
замінена на ON автоматикою, поки аварія активна. Доступ UI до інтернету не публікується.

## Ротація та експлуатація

Для ротації device-пароля зупиніть стенд, замініть відповідний секрет у `.env` на
48 випадкових hex-символів, запустіть bootstrap, потім compose up. Не видаляйте тільки
password_file: simulator/openHAB і брокер мають отримати узгоджені облікові дані.
У production — окремі хости/секрети пристроїв, резервне живлення, hardware interlocks,
обмеження частоти, зовнішній моніторинг, захищений доступ до UI через VPN/HTTPS.
