# Власна відеодемонстрація: орієнтовно 9 хвилин

Це план для живого пояснення, не готовий відеозапис. Вкажіть свої ПІБ і групу.
Запис 1280×720 або вище, читабельний термінал, власний голос. Розділи 3–6 запишіть
одним дублем без склейок. Не показуйте `.env`, password_file, приватні ключі чи пароль MainUI.

## До початку запису

1. Виконайте bootstrap, один раз завантажте образи/add-ons і створіть локального адміністратора.
2. Перевірте normal, smoke і security tests, дочекайтеся появи графіка.
3. Відкрийте три термінали: compose-команди, MQTT-потік, логи. Поруч — BasicUI.
4. Збільште шрифт. Підготуйте README з діаграмою і відкритий вихідний код.

Підготовлені образи/сертифікати не заважають показати «запуск з нуля»: у записі
контейнери зупиняються командою down й запускаються знову, без прихованого ручного налаштування.
Поясніть, що перше завантаження add-ons було виконане раніше, а історію графіка збережено у volume.

## Команди для розділів 3–6

```bash
docker compose down
docker compose up -d
docker compose ps
docker compose exec simulator python devices.py --scenario normal
docker compose run --rm tools scripts/watch.py
```

В іншому терміналі послідовно перемикайте сценарії (кожна команда окремо):

```bash
docker compose exec simulator python devices.py --scenario hot
docker compose exec simulator python devices.py --scenario critical
docker compose exec simulator python devices.py --scenario leak
docker compose exec simulator python devices.py --scenario ups
docker compose exec simulator python devices.py --scenario offline-hot
docker compose exec simulator python devices.py --scenario normal
docker compose run --rm tools scripts/security_check.py
docker compose logs --since 5m mosquitto
```

Для offline-hot почекайте понад хвилину; використайте цей час, щоб пояснити keepalive,
Last Will і відмінність online від свіжості телеметрії. Не вирізайте очікування з розділів 3–6.
Якщо показ усіх подій займає довше, загальну тривалість можна збільшити до 10 хвилин.

## Питання до захисту

| Питання | Орієнтир для власної відповіді |
|---|---|
| Чому QoS 1? | Низька частота, цінність аварійних подій, допустимі дублікати; встановлення стану ідемпотентне |
| Що після SIGKILL? | Немає DISCONNECT; після виявлення обриву брокер публікує retained offline; watchdog вмикає тривогу |
| Навіщо freshness, коли є LWT? | Застосунок може зависнути, але MQTT-loop продовжить PING; online без вимірів не означає справність |
| Пароль сенсора викрадено — що далі? | Автентифікацію пройдено, але ACL не дає писати set іншого пристрою; власну телеметрію можна підробити |
| Автентифікація й авторизація? | password_file встановлює особу; acl_file визначає дозволені дії/топіки |
| Навіщо autoupdate=false? | UI чекає state від актуатора, а не вважає команду виконаною одразу |
| Де edge/fog? | Пристрій перевіряє/виконує команду на edge; зведені правила й історія у локальному fog/openHAB |
| Як не скинути чужу тривогу? | Підсумковий OR усіх активних причин; єдине місце команд сирені |

Можлива жива зміна: змінити 35 на 34 у модулі server-policy, пояснити нове спрацювання;
або додати читача MQTT із ACL тільки telemetry. Не давайте новому читачу `readwrite #`.
Особистий висновок про власні знання сформулюйте після реального запуску та вивчення коду.
